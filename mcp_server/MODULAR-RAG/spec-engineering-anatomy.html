PART I

Spec 本身的工程化

大多数项目的设计文档写完就死了 — 它描述的是一个再也不会被验证的过去。这份 spec 之所以还活着，靠的是六个具体机制。

S1

七章是一个收敛漏斗，不是章节列表

章节顺序本身编码了决策的依赖方向：为什么做（1 概述／设计理念）→ 做什么（2 核心特点）→ 怎么选（3 技术选型）→ 怎么算做好（4 测试方案）→ 长什么样（5 架构与模块）→ 怎么落地（6 排期）→ 不做什么（7 未来展望）。

注意第 4 章（测试方案）排在第 5 章（架构）之前。质量契约先于结构确定 — 这是 TDD 思路在文档层面的体现：先说清怎么验证，再说清怎么构造。第 7 章「未来展望」的真实作用是显式划定当前范围的边界，把"想做但这一版不做"的东西写下来，避免范围蔓延时无据可依。

为什么

能这样排的文档，读者可以在任何一章停下来并且知道自己缺什么。按"数据库设计 / 接口设计 / 部署"分章的文档做不到，因为那是实现视角的切片，不是决策视角的漏斗。

S2

目录树被声明为「交付清单」，架构图因此可验收

这是整份 spec 里最锋利的一句话。它出现在第 6 章排期原则的第一条：

只按本文档设计落地：以第 5.2 节目录树为"交付清单"，每一步都要在文件系统上产生可见变化。

一句话把第 5.2 节的目录树从装饰变成了契约。架构图通常无法验收，因为"分层清晰"不是一个可判定的命题；但"src/libs/reranker/base_reranker.py 是否存在"是。于是架构与交付物之间建立了双向绑定：代码缺了文件，spec 就失守；spec 改了结构，代码必须跟。

为什么

把抽象的架构约束降维成文件系统上的布尔判断，架构评审才有了可以机械执行的部分。这也是为什么 Part IV 的漂移能被一条 ls 查出来。

S3

任务卡六要素：目标 / 前置 / 文件 / 签名 / 验收 / 命令

68 个任务全部遵循同一个模板。以 D5（混合检索编排）为例，去掉散文后剩下的是：

DEV_SPEC.md · D5：HybridSearch 编排
目标      实现 hybrid_search.py：编排 Dense + Sparse + Fusion，集成 Metadata 过滤
前置依赖  D1(QueryProcessor) D2(Dense) D3(Sparse) D4(Fusion)
修改文件  src/core/query_engine/hybrid_search.py
          tests/integration/test_hybrid_search.py
实现签名  HybridSearch.search(query, top_k, filters?, trace?) -> List[RetrievalResult]
          HybridSearch._apply_metadata_filters(candidates, filters)
内部流程  process() → 并行(dense + sparse) → fuse() → metadata_filter → Top-K
验收标准  · 对 fixtures 数据返回 Top-K（含 chunk 文本与 metadata）
          · 支持 filters 参数过滤
          · Dense/Sparse 任一路径失败时能降级到单路结果
测试方法  pytest -q tests/integration/test_hybrid_search.py

三个细节决定了这张卡能不能用。第一，修改文件里包含测试文件——测试不是任务的附属品，是交付物的一部分。第二，实现签名写到参数级，包括 filters? 和 trace? 这两个可选参数，接口在编码前就定死了，下游任务可以并行开工而不必等上游写完。第三，也是最容易被跳过的：验收标准里写了失败路径。"任一路径失败时能降级到单路结果"——绝大多数任务描述只写happy path，于是降级逻辑永远是事后补的、没测过的。

为什么

对比常见写法"实现混合检索"：无法验收（什么算实现完）、无法并行（接口未定）、无法交接（改哪些文件不知道）、无法回归（没有命令）。六要素把这四个问题一次性解掉。

S4

一小时粒度：不是估时，是上下文容量的约束

1 小时一个可验收增量：每个小阶段（≈1h）都必须同时给出"验收标准 + 测试方法"，尽量做到 TDD。

这个粒度是被人（或 agent）能在一次不中断的工作里保持的状态量决定的，而不是被工作量决定的。任务大到需要跨天，中途的假设、试错记录、临时结论就会丢失；小到十分钟，编排开销就超过了实现开销。68 个任务 ÷ 9 个阶段 ≈ 每阶段 7~8 张卡，恰好是一个阶段能在一两天内闭环的量。

阶段本身的排序原则同样写明了：

先打通主闭环，再补齐默认实现：优先做"可跑通的端到端路径（Ingestion → Retrieval → MCP Tool）"，并在 Libs 层补齐可运行的默认后端实现，避免出现"只有接口没有实现"的空转。

  1. A工程骨架可导入 → 可测试
  2. BLibs 可插拔层抽象 + 默认实现
  3. CIngestionPDF → 向量库
  4. DRetrievalHybrid + RRF + Rerank
  5. EMCP Server对外可用
  6. FTrace双链路打点
  7. GDashboard六页面
  8. H评估体系可量化回归
  9. I验收收口E2E + README

可观测性（F）排在主链路（C/D/E）之后，是个有意识的取舍：先让系统能跑，再让它透明。但请看下一条 —— 这个"之后"被提前做了准备。

S5

为未来阶段预留参数位，避免后期签名重构

阶段 B 写 BaseLLM 时，Trace 基础设施要到阶段 F 才做。常规做法是 F 阶段回来给所有接口加参数 —— 那是一次波及全代码库的签名变更。这里的做法是在 B 阶段就把位置留出来：

src/libs/llm/base_llm.py
@abstractmethod
def chat(
    self,
    messages: List[Message],
    trace: Optional[Any] = None,   # ← B 阶段就存在
    **kwargs: Any,
) -> ChatResponse:
    """...
    Args:
        trace: Optional TraceContext for observability
               (reserved for Stage F)
    """

注释里直接写了 reserved for Stage F。同样的 trace? 出现在 D2/D3/D5/D6 的任务签名里。到了 F 阶段，打点变成在函数体内加几行 record_stage()，没有一处调用方签名需要改。

为什么

接口的形状比接口的实现贵得多。形状定错，改动成本随调用点数量线性增长；实现定错，成本局限在一个文件内。所以对已经确定会来的横切关注点（追踪、鉴权、租户），预留参数位是便宜的保险。

S6

进度表内嵌在 spec 里，测试数量充当交付凭证

状态不在 Jira 里，在 spec 第 6 章的表格里：[ ] 未开始 / [~] 进行中 / [x] 已完成，外加完成日期和备注。备注的写法值得注意：

DEV_SPEC.md · 进度跟踪表（节选）
B1   LLM 抽象接口与工厂      [x] 2026-01-27  BaseLLM + LLMFactory + 16个单元测试
C13  ImageStorage            [x] 2026-02-01  ImageStorage + SQLite索引 + 37个单元测试 + WAL并发支持
D6   Reranker（Core 编排）    [x] 2026-02-04  CoreReranker + Fallback机制 + 27单元测试 + 7集成测试
I1   E2E：MCP Client 模拟     [x] 2026-02-23  7个E2E测试 + import死锁修复 + 非阻塞readline

每条备注都以测试数量结尾。"完成"被定义为"有多少个测试在守着它"，而不是"我觉得写完了"。I1 那条还记下了过程中遇到的真实故障（import 死锁、阻塞 readline）—— 这些是未来最容易复发的坑，写在这里比写在 commit message 里更容易被下一个人看到。

为什么

文档与进度同源，文档就不会腐烂：改状态时你必然重新读到它旁边的设计。反之，一旦进度搬去外部工具，spec 就退化成一次性的立项材料。

PART II

架构决策与其代码证据

spec 第 3.3.1 节列了四条设计原则：接口隔离、配置驱动、工厂模式、优雅降级。原则是免费的，下面看它们在代码里兑现成了什么。

D1

四层 + 横切，依赖方向严格单向

依赖方向（箭头 = 允许依赖）
MCP Server 层   tools/ · protocol_handler        ← 接口，只做协议与格式化
      │
      ▼
Core 层         query_engine/ · response/       ← 业务编排，只依赖抽象
      │
      ▼
Libs 层         base_*.py + *_factory.py        ← 可插拔抽象 + 具体实现
      │
      ▼
Storage         Chroma · BM25 · SQLite · 文件系统

Ingestion       离线链路，与 Core 平级，共用 Libs 与 core/types
Observability   横切，被各层可选注入，不反向依赖任何层

关键约束是 Libs 层不认识 Core 层。llm_factory.py 里唯一的 Core 引用是类型标注，且被 TYPE_CHECKING 隔离，运行时不产生依赖：

src/libs/llm/llm_factory.py
if TYPE_CHECKING:
    from src.core.settings import Settings   # 仅静态检查可见

Core 依赖的是 BaseLLM 而不是 AzureLLM —— 依赖倒置在这里不是口号，它的可观察后果是：删掉 azure_llm.py，Core 层一行都不用改。

D2

数据契约中心化，并在构造期 fail-fast

src/core/types.py 是全链路共用的契约中心，spec 里的定位是「作为 ingestion / retrieval / mcp 的数据契约中心」。文件头的 docstring 说明了动机：

src/core/types.py
Design Principles:
- Centralized contracts: All stages use these types to avoid coupling
- Serializable: All types support dict/JSON conversion
- Extensible metadata: Minimum required fields with flexible extension

更值得学的是校验的时机：

src/core/types.py · Document
def __post_init__(self):
    """Validate required metadata fields."""
    if "source_path" not in self.metadata:
        raise ValueError("Document metadata must contain 'source_path'")

source_path 是引用溯源的根，缺了它整条链路后面的 citation 都无从生成。把校验放在 __post_init__，意味着非法对象不可能被构造出来 —— 错误在 Loader 里就炸，而不是在几个阶段之后的 ResponseBuilder 里以一个 KeyError 的形式出现。

为什么

流水线型系统的调试成本，几乎完全由"错误发生点"与"错误暴露点"之间的距离决定。契约在构造期自检，就是把这个距离压到零。而 metadata 保持 dict 开放扩展，则避免了为每个新字段改动所有阶段。

D3

可插拔三件套，与注册表工厂的四个细节

六类组件（LLM / Embedding / Splitter / VectorStore / Reranker / Evaluator）用的是完全相同的三文件结构：base_xxx.py 定义 ABC，xxx_factory.py 做注册与路由，具体实现各占一个文件。真正的工程含量在工厂的四个细节：

src/libs/llm/llm_factory.py
# ① 注册表，而非 if/elif 链
_PROVIDERS: dict[str, type[BaseLLM]] = {}
_VISION_PROVIDERS: dict[str, type[BaseVisionLLM]] = {}

# ② 注册时校验继承关系，错误在注册点暴露
def register_provider(cls, name, provider_class):
    if not issubclass(provider_class, BaseLLM):
        raise ValueError(f"{provider_class.__name__} must inherit from BaseLLM")
    cls._PROVIDERS[name.lower()] = provider_class

# ③ 错误信息里给出可选项
available = ", ".join(sorted(cls._PROVIDERS.keys())) or "none"
raise ValueError(f"Unsupported LLM provider: '{provider_name}'. "
                 f"Available providers: {available}.")

# ④ 可选依赖缺失不阻塞模块加载
def _register_vision_providers():
    try:
        from src.libs.llm.azure_vision_llm import AzureVisionLLM
        LLMFactory.register_vision_provider("azure", AzureVisionLLM)
    except ImportError:
        pass   # 该 provider 不可用，但工厂本身照常工作

① 让新增 provider 不必修改工厂代码；② 把"实现没继承基类"这类错误从调用时提前到注册时；③ 是一个纯粹的人机工程决定 —— 配置写错时，报错信息直接告诉你有哪些合法值，省掉一次翻文档；④ 是优雅降级在模块加载期的体现：没装 Vision 依赖的环境，文本 LLM 照常可用，而不是整个工厂 import 失败。

为什么

工厂模式人人会写，区别全在这些边缘：注册校验、错误信息的信息量、可选依赖的隔离。它们决定了这个扩展点是真的好用，还是只在架构图上好看。

D4

优雅降级必须留痕，否则等于静默的质量劣化

降级在三个层次都实现了，而且都遵循同一个纪律 —— 降级了就要在返回结构里说出来。

src/core/query_engine/reranker.py
@dataclass
class RerankerConfig:
    fallback_on_error: bool = True        # 可关闭，便于测试暴露真实异常

@dataclass
class RerankResult:
    results: List[RetrievalResult]
    used_fallback: bool = False           # ← 降级标记进入返回值
    fallback_reason: Optional[str] = None # ← 原因一并带出

# 失败路径
except Exception as e:
    logger.warning(f"Reranking failed, using fallback: {e}")
    if self.config.fallback_on_error:
        # 退回 fusion 原序，并逐条打标
        ... metadata["rerank_fallback"] = True ...
        return RerankResult(results=..., used_fallback=True,
                            fallback_reason=str(e))
    raise RerankError(f"Reranking failed and fallback disabled: {e}") from e
层次降级行为留痕方式
CoreReranker退回 fusion 排序used_fallback + fallback_reason + chunk 级 rerank_fallback
HybridSearchDense/Sparse 任一路失败 → 单路结果used_fallback 进入 trace
DocumentManager四存储逐个删，失败不中断其余每个存储一个布尔字段回报
LLMFactoryVision provider 注册失败从 list_vision_providers() 中消失

这些标记随 trace 落进 logs/traces.jsonl，Dashboard 的 Query 追踪页能看到。

为什么

不留痕的降级是最危险的一类 bug：系统永远"可用"，质量却在悄悄下滑，而指标下降时你无法区分是模型退化、数据变化，还是某个后端已经连续三周在 fallback。降级标记是可用性与可观测性之间的必要连接。

D5

三段式 stable ID 换来 upsert 幂等

src/ingestion/storage/vector_upserter.py
chunk_id = f"{source_hash}_{chunk_index:04d}_{content_hash}"
#            └─ SHA256(source_path)[:8]
#                          └─ 文档内序号，零填充
#                                        └─ SHA256(chunk.text)[:8]

source_hash  = hashlib.sha256(source_path.encode("utf-8")).hexdigest()[:8]
content_hash = hashlib.sha256(chunk.text.encode("utf-8")).hexdigest()[:8]
# → "a1b2c3d4_0000_e5f6g7h8"

三个段各自承担一个职责：source_hash 划定归属，使按文档删除成为一次前缀匹配；零填充序号让 ID 的字典序等于 chunk 的自然顺序（_0010 排在 _0002 之后，而非之前）；content_hash 让"同内容 → 同 ID"，重复摄取直接覆盖而不产生重复行。

配合 FileIntegrity 的 SHA256 文件级记录（data/db/ingestion_history.db），构成两级幂等：文件未变直接跳过整个流水线，文件变了则逐 chunk 判定哪些需要重写。

为什么

摄取流水线最常见的事故是"重跑一次，数据翻倍"。让 ID 由内容决定而非由自增序列决定，幂等性就成了数据结构的性质，而不需要靠调用方记得先删再写。代价：内容变化会产生新 ID，孤儿记录的清理必须由 DocumentManager 显式负责 —— 这一点 spec 交代得不够，见 X3。

D6

Trace 显式注入；两套时钟各司其职

spec 第 3.4.1 节把追踪的侵入性列为设计目标：「追踪逻辑与业务逻辑解耦，通过 TraceContext 显式调用模式注入，避免污染核心代码」。实现上选的是显式传参（trace: Optional[Any] = None），而不是 contextvar 或线程局部的隐式上下文。

取舍很清楚：显式传参污染签名，但换来两件事 —— 函数签名本身就声明了"这个函数会打点"，以及单元测试不需要 mock 任何全局状态，传个假 trace 进去即可。对于一个以"链路可见"为教学目标的项目，这是对的选择。

时间处理上有一个容易写错的细节：

src/core/trace/trace_context.py
# 给人看的时间戳：带时区的 ISO-8601 挂钟时间
started_at: str = field(
    default_factory=lambda: datetime.now(timezone.utc).isoformat())

# 算耗时的时钟：单调时钟，不受系统时间调整 / NTP 校正影响
_start_mono: float = field(default_factory=time.monotonic, repr=False)

def elapsed_ms(self, stage_name=None) -> float:
    end = self._finish_mono if self._finish_mono is not None else time.monotonic()
    return (end - self._start_mono) * 1000.0

用 time.time() 相减算耗时，遇到 NTP 回拨就会得到负数或荒谬的大值。这里挂钟时间只用于展示，单调时钟只用于测量，两者不混用。

D7

可插拔性要一直贯穿到 UI 才算端到端

所有页面基于 Trace 中的 method / provider 字段动态渲染，更换可插拔组件后 Dashboard 自动适配，无需修改代码。

这是一条很容易被忽略的一致性要求。如果 Dashboard 里硬编码了 "Azure OpenAI" 或者把 rerank 阶段写死成"Cross-Encoder 重排"，那么把 provider 换成 Ollama 之后，架构仍然是可插拔的，但可观测层开始说谎。解决办法是让每个阶段把自己的 method/provider 写进 trace，UI 只负责渲染读到的值。

为什么

可插拔架构的常见失败不在核心链路，而在它的外围：监控面板、日志格式、报表、告警规则里散落的硬编码后端名。判断标准很简单 —— 换一个 provider，有多少个文件需要改？答案必须是「一个：settings.yaml」。

D8

协议的硬约束，要写进验收标准

MCP 的 stdio transport 有一条致命约束：stdout 是协议通道，任何一行多余的 print() 都会破坏 JSON-RPC 帧。spec 把它直接写成了 E1 的验收条件：

DEV_SPEC.md · E1：MCP Server 入口与 Stdio 约束
目标      遵循"stdout 只输出 MCP 消息，日志到 stderr"
验收标准  启动 server 能完成 initialize；stderr 有日志但 stdout 不污染
测试方法  pytest -q tests/integration/test_mcp_server.py（子进程方式）

注意测试方法特别注明了子进程方式。在同进程里断言 stdout 干净是无效的 —— 只有真的把 server 作为子进程拉起、读它的两个流，才能检出污染。一个在 import 期打印 banner 的第三方库，只有这种测法能抓到。

为什么

这类"环境级约束"（stdout 洁净、不得写入工作目录、必须幂等退出）不属于任何一个函数，因此天然不会出现在单元测试里。它们唯一的归宿就是验收标准，并且必须指定能检出它们的测试形态。

PART III

测试工程

spec 第 4 章声明了测试金字塔。声明金字塔的项目很多，比例真的成金字塔的不多。

T1

金字塔的真实比例：12 : 3 : 1

层测试文件spec 目标作用
tests/unit49核心逻辑覆盖率 ≥ 80%秒级反馈，全 mock 外部依赖
tests/integration12关键路径 100%验证模块协作与数据契约
tests/e2e4核心场景 100%子进程拉起 MCP / Dashboard 冒烟

比例约 12 : 3 : 1，形状正确。I5 的验收备注记录了最终规模：1198 单元 + 30 e2e 通过。值得留意的是 e2e 的四个文件覆盖的是形态而非功能：MCP 客户端模拟、Dashboard 冒烟、摄取、召回回归 —— 每一个都在验证一种"只有真实环境才暴露的问题"，而不是重复单元测试已经覆盖的逻辑。

T2

用 marker 把「要花钱的测试」隔离出去

pyproject.toml
markers = [
    "unit: Unit tests (fast, no external dependencies)",
    "integration: Integration tests (may require external services)",
    "e2e: End-to-end tests (full system tests)",
    "llm: marks tests that require real LLM API calls (deselect with '-m \"not llm\"')",
    "slow: Slow tests that should be run less frequently",
]

llm 这个 marker 是整个测试配置里最实用的一项。RAG 项目的测试有一类特殊成本：调用真实 LLM 既慢又花钱，还会因为模型输出不确定而偶发失败。把它们标出来之后，日常迭代跑 pytest -m "not llm"，需要验证真实集成时再单独跑。

为什么

如果昂贵测试和廉价测试混在一起，结果一定是整个测试套件被放弃 —— 没人会为了改一行代码等五分钟并花掉几块钱。marker 的价值不在分类，在于保住了"高频运行"这个习惯。

T3

构造函数注入依赖，换取不打 patch 的可测性

spec 在 D2/D3 的任务卡里明确注明「支持依赖注入用于测试」，代码照做：

src/core/query_engine/dense_retriever.py · document_manager.py
class DenseRetriever:
    def __init__(self,
                 settings: Optional[Settings] = None,
                 embedding_client: Optional[BaseEmbedding] = None,
                 vector_store: Optional[BaseVectorStore] = None): ...

class DocumentManager:
    def __init__(self, chroma_store, bm25_indexer,
                 image_storage, file_integrity): ...   # 四个存储全部注入

可选参数的语义是：传了就用，没传就按 settings 造。生产代码走后者（一行 DenseRetriever(settings)），测试走前者（塞进假的 embedding 和假的 store）。DocumentManager 更彻底 —— 四个存储全部必须注入，它自己不知道怎么创建它们。

为什么

替代方案是 unittest.mock.patch 打补丁。补丁依赖于被测代码的 import 路径，重构一次就断一片；而且它不会迫使你想清楚依赖边界。注入把依赖写在签名里，难以注入的类，通常就是职责过载的类 —— 可测性在这里充当了设计的体检指标。

PART IV · 待改进

失守之处

只讲优点的拆解没有学习价值。下面四条是我在核对 spec 与代码时实际查出来的问题 —— 它们恰好都是 spec 驱动开发最典型的失效模式。

X1

Spec 漂移：目录树声明了五处不存在的交付物

S2 把第 5.2 节目录树定为「交付清单」。既然是清单，就可以核对。核对结果：

spec 5.2 声明实际
libs/splitter/semantic_splitter.py不存在
libs/splitter/fixed_length_splitter.py不存在
libs/evaluator/ragas_evaluator.py实际落在 observability/evaluation/
requirements.txt不存在（依赖统一在 pyproject.toml）
架构图中的 search_by_keyword tool未实现（tools/ 下只有 3 个）

这几处的性质不同，处理方式也应不同。semantic_splitter / fixed_length_splitter / search_by_keyword 属于规划中但未实现 —— 它们应当从 5.2 的交付清单移到第 7 章「未来展望」，否则清单的可验收性就打了折扣。ragas_evaluator 的位置分歧更值得注意：它已经实现了，只是落在 observability/evaluation/ 而非 spec 说的 libs/evaluator/。这意味着 Evaluator 的可插拔边界在实现过程中被移动了，而 spec 没有跟上 —— 现在 libs/evaluator/ 下只有 base、factory 和 custom，真正的 Ragas 后端在另一层。requirements.txt 是纯粹的历史残留，删掉这一行即可。

教训

把目录树当交付清单是个好机制，但它需要配套的反向校验：一个遍历 5.2 目录树、逐个 os.path.exists() 的脚本，跑在 CI 里，几十行就够。声明了可验收性却不去验收，机制就退化成了文档承诺。

X2

218 KB 单文件已经越过维护极限 —— 工具链已经在替它打补丁

DEV_SPEC.md 现在是 3,214 行 / 218 KB。最直接的证据不是文件大小，而是项目自己造了个工具来对付它：

.claude/skills/auto-coder/
scripts/sync_spec.py        ← 把 DEV_SPEC.md 切成 7 份
references/01-overview.md      02-features.md     03-tech-stack.md
           04-testing.md       05-architecture.md 06-schedule.md
           07-future.md

SKILL.md 中的读取策略：
| 06-schedule.md   | 任务排期与状态 | 每个周期都读 |
| 05-architecture.md | 架构与模块设计 | 新建/修改模块时读 |

需要先拆分才能消费，说明单文件已经超出了单次可加载的粒度。而拆分脚本本身又引入了新风险：派生副本可能与源文件不同步 —— 现在有两份架构描述，一份在 DEV_SPEC 第 5 章，一份在 references/05-architecture.md。

教训

更省事的做法是从一开始就按章分文件（spec/01-overview.md … spec/07-future.md）+ 一个索引页，让人和工具读同一份文件。判断时机的经验信号很简单：当你开始为文档写解析脚本，就该拆文件了。

X3

跨四存储删除没有一致性模型，取舍只在代码注释里

DocumentManager.delete_document() 要依次删除四个存储：Chroma 向量、BM25 索引、图片文件 + SQLite 索引、摄取历史记录。策略写在源文件的 docstring 里：

src/ingestion/document_manager.py
- Fail-safe: partial failures are reported but do not abort remaining stores.

@dataclass
class DeleteResult:
    chunks_deleted: int = 0
    bm25_removed: bool = False
    images_deleted: int = 0
    integrity_removed: bool = False

这是一个合理的选择（尽最大努力删除，逐存储回报结果），但它意味着系统接受中间态的存在：Chroma 删成功、BM25 失败，就会留下 BM25 能召回、但 get_by_ids 取不到内容的悬空 chunk_id。SparseRetriever 的流程正是 bm25.query() → vector_store.get_by_ids()，这条路径会命中这个不一致。

问题不在于选了尽力删除 —— 本地单用户场景下这远比引入分布式事务合理。问题在于这个取舍只存在于代码注释里，spec 第 5 章从未讨论一致性模型：没有说明可能出现哪些中间态、谁负责收敛、要不要提供一个校验/修复入口。D5 也提到内容变更会产生新 chunk_id，孤儿记录的清理责任同样悬空。

教训

凡是跨越多个存储的写操作，spec 都该有一小节回答三个问题：可能出现哪些不一致状态？谁负责发现？怎么修复？哪怕答案是"接受不一致，提供一个 verify --repair 命令"，写下来也远好过留给下一个人从注释里考古。

X4

「声明即完成」的错觉：抽象层的兑现率需要单独跟踪

spec 第 5.3.5 节用一张表列出了每个抽象的「可替换选项」：VectorStore 可换 Qdrant / Pinecone / Milvus，Embedding 可换 BGE / Ollama，Splitter 可换 Semantic / FixedLen。进度表显示 68/68 任务 100% 完成。两者叠在一起，很容易读成"这些替换都可用了"。

实际情况：VectorStore 只有 Chroma 一个实现，Splitter 只有 Recursive 一个实现，Loader 只有 PDF 一个。这本身完全正常 —— 阶段 B 的原则就是"至少有一个默认后端可跑通"。但它引出一个真实的技术风险：只有一个实现的抽象接口，无法证明自己真的是抽象的。

接口是否漏了底层细节，只有在接入第二个实现时才会暴露。BaseVectorStore 现在包含 get_by_ids()（D3 任务为了 BM25 回查文本而追加的方法）—— 这个方法签名是围绕 Chroma 的能力形成的，换 Pinecone 时是否仍然自然，目前无从得知。

教训

抽象层的可信度应当单独跟踪，而不是混进任务完成率。可行的做法有两种：其一，为每个抽象写一套契约测试（任何实现都必须通过的同一批用例）—— 项目在 I4 已经做了一部分（"VectorStore + Reranker + Evaluator 边界测试"），值得继续扩展；其二，给每个抽象接一个极简的第二实现（哪怕是内存版 InMemoryVectorStore），仅用于证明接口没有泄漏底层假设 —— 它同时还会让单元测试彻底摆脱 Chroma。

可迁移清单

下次你写一份 spec 或设计一个可插拔系统时，这些是能直接搬走的判断标准。

  • 章节顺序是决策漏斗，不是实现切片：为什么 → 做什么 → 怎么选 → 怎么验收 → 长什么样 → 怎么落地 → 不做什么。
  • 把架构约束降维成文件系统上的布尔判断：目录树即交付清单 —— 并且写一个脚本真的去校验它（X1 的教训）。
  • 任务卡六要素：目标 / 前置依赖 / 修改文件（含测试）/ 实现签名 / 验收标准 / 可复制的测试命令。缺一项，任务就无法并行或无法交接。
  • 验收标准必须包含失败路径。"X 失败时降级到 Y 并标记" 这类条目，是降级逻辑唯一会被真正实现和测试的地方。
  • 任务粒度由上下文容量决定，不由工作量决定。≈1 小时，一个可验收增量。
  • 为确定会来的横切关注点预留参数位（trace?、tenant?）。接口的形状比实现贵得多。
  • 进度与文档同源，完成的定义是"有多少测试在守着它"，并把踩过的坑写进备注。
  • 契约在构造期自检（__post_init__），把错误发生点与暴露点的距离压到零。
  • 工厂用注册表而非 if/elif；注册时校验继承；错误信息里列出合法可选项；可选依赖用 try/ImportError 隔离。
  • 降级必须留痕：used_fallback + reason 进返回值、进 trace、进面板。静默降级是最难查的一类质量事故。
  • 幂等靠内容寻址，不靠调用方自觉：ID 由 source + index + content hash 决定。
  • 挂钟时间只用于展示，单调时钟只用于测量。两者永不混用。
  • 换一个后端要改几个文件？答案必须是一个：settings.yaml。面板、日志、报表里的硬编码后端名都算破功。
  • 环境级约束写进验收标准，并指定能检出它的测试形态（stdout 洁净 → 必须子进程测）。
  • 用 marker 隔离昂贵测试（-m "not llm"），保住"高频运行"这个习惯。
  • 跨存储写操作要在 spec 里回答三问：可能出现哪些不一致？谁负责发现？怎么修复？
  • 只有一个实现的抽象不算被验证过。补契约测试，或补一个内存版第二实现。
  • 当你开始为文档写解析脚本，就该拆文件了。
